# 视觉驱动自动化脚本 —— 开发方法论

> 适用任务类型：**用视觉识别 + 模拟输入去驱动一个不可编程的外部界面**
> （云游戏自动化、GUI 脚本、录制回放、RPA、游戏辅助等）
>
> 本文沉淀自 `naruto-auto`（火影忍者云游戏自动化）的实战返工教训。
> 目的：**同类任务不再犯同样的错、走同样的弯路。**

---

## 0. 核心命题

这类任务的返工，**几乎从来不来自"代码写错"**，而来自三类信息缺口：

| 缺口 | 表现 | 本项目实例 |
|---|---|---|
| **负样本缺失** | 只知道"对的什么样"，不知道"错的什么样" → 判据阈值定错 | 距离阈值定 60，真值 81 → 弹窗永远识别不出 → 死循环 |
| **意图未标注** | 代码里没有权威答案，只能推断 → 推错 | 9 处拖动里 6 处方向标错 |
| **作用域未清点** | 改了共享资源，不知道谁依赖它 | 拖动安全区收窄后，另一任务的位移从 700px 缩到 17px |

**共同点：这三类缺口都不是靠"更努力写代码"能补上的，只能靠开工前的信息采集。**

---

## 1. 开工前：四层信息采集

### 1.1 意图层 —— 决定"做什么"

必须问清，**不可推断**：

- 是**复刻**还是**重新设计**？
  （复刻 = 1:1 照录制；重设计 = 可改时序/换探针。方向完全不同）
- 哪些环节**必须一致**、哪些**允许优化**？
- 交付标准是**跑通一次**还是**长期稳定挂机**？
  （决定容错、重试、超时要不要做）

### 1.2 判据层 —— 决定"怎么判定"

**每个需要识别的画面，都要问两件事：**

```
① 误识别（假阳性）和漏识别（假阴性），哪个后果更严重？
② 识别失败时期望：重试 / 跳过 / 停止？
```

**为什么关键** —— 这直接决定阈值往哪边偏：

| 识别目标 | 漏识别后果 | 误识别后果 | 阈值方向 |
|---|---|---|---|
| 退出确认弹窗 | **死循环卡死**（严重） | 多点一下（无害） | **放宽** |
| 战斗结算检测 | 继续打（浪费） | 提前收手（丢一场） | 收紧 |
| 日常任务入口 | 任务失败（可重试） | 点错页面（可能更糟） | 看情况 |

**教训**：本项目没问就直接按"看起来严格"定了阈值，恰好卡死。
**若先问"漏识别是不是更严重"，答案显然是"是"，阈值自然放宽，一次就对。**

### 1.3 语言层 —— 消除歧义

**强制约定：方向只说结果，不说手势。**

```
❌「从右往左滑」   → 歧义：指手指？还是指画面内容？
✅「拖到最右」     → 唯一解释
```

**本项目代价**：来回纠正 3 次，还写反过常量名。
**最终方案**：代码里固化成 `dragScene(ctx, 'left' | 'right')` —— **从 API 层面消灭歧义**。

> **推广**：任何有歧义的表述，都要在开工时翻译成唯一语义并**写进代码命名**，
> 而不是靠记忆和默契。

### 1.4 环境层 —— 锁定坐标基准

| 必问 | 为什么 |
|---|---|
| 逻辑分辨率 / 目标实际分辨率 | 坐标换算的基础 |
| 录制文件的坐标基准 | 可能与实时画面不一致（本项目：录制 1280×720 vs 截图 1920×1080） |
| 是否有黑边 / DPI 缩放 | 会影响映射 |

> **法则：坐标体系不确认，一切坐标都不可信。**
> 必须先做一次「基准对齐验证」—— 拿一个已知点，在录制坐标和实时画面上各测一遍，
> **数值一致才继续。**

## 2. 样本采集：正负成对（铁律）

> **每个探针必须拿到「正样本 + 负样本」，并实测两者的数值分布。**

### 正确做法

```
正样本（目标存在）:    指标A=0.839   指标B=81
负样本（目标不存在）:  指标A=0.005   指标B=157
                                    ↓
阈值取中间并留余量:    指标A>=0.5    指标B<=120
```

### 反例（本项目踩的坑）

```
只看正样本: 指标B≈0（来自一张色差很大的截图）
            ↓
     拍脑袋定: 指标B<=60
            ↓
     实机真值: 指标B=81  →  永远不通过  →  死循环
```

> **本项目唯一一次"一次就成"的修复，恰恰是因为第一次同时看到了两个数（81 vs 157）。**
> 差别就在这里。

### 样本清单模板

| # | 样本 | 谁提供 | 备注 |
|---|---|---|---|
| 1 | 完整操作录制文件 | **用户** | 时序、坐标、键序来源 |
| 2 | 每个关键界面的**正样本**截图 | **用户** | 基准分辨率 |
| 3 | 每个关键界面的**负样本**截图 | **用户** | ⭐ 最易缺、最关键 |
| 4 | 各动作的**期望结果清单**（方向/次数/顺序） | **用户** | ⭐ 最易缺 |
| 5 | 键位/元素语义表 | 用户或推导 | 推导需标注"未确认" |
| 6 | 一份「标准成功日志」 | **用户** | 验收基线 |

> **关键洞察**：样本缺口**几乎全部集中在"负样本"和"意图标注"** ——
> 也就是**只能从用户那里得到、且只需用户花几分钟**的信息。

## 3. 工具：先建工具，再动主脚本

### 3.1 分工原则

| 类型 | 谁做 | 例子 |
|---|---|---|
| **只有用户能做** | 用户配合 | 录制、制造特定画面、真机验证 |
| **应开工前建好** | 我 | 帧提取、探针测试、影响面审计 |
| **边做边造（应避免）** | — | 临时脚本、一次性脚本 |

### 3.2 四个必备工具

| # | 工具 | 用途 |
|---|---|---|
| 1 | **帧提取器** | 从 trace/日志导出关键帧 → 校准素材来源 |
| 2 | **探针测试器** | 喂图片 → 输出判据数值 → **强制打印正负样本对比** |
| 3 | **影响面审计器** | `grep` 出某模式/常量的**全部**使用点（防"改一处漏九处"） |
| 4 | **实时抓取器** | 抓当前画面做即时校准 |

### 3.3 为什么"先建工具"

> **主脚本改一次 = 推送 → 用户跑一轮 → 贴日志**，反馈周期以**轮**计。
> **工具跑一次 = 秒级。**
>
> 把能自动化的验证都放进工具，**反馈成本从"一轮"降到"一秒"**。

---

## 4. 开发执行：三条纪律

### 纪律 1 —— 改共享资源前，先清点影响面

> **任何共享常量 / 公共函数被修改前，必须 `grep` 出所有使用点，逐个判断。**

❌ 反例：改拖动安全区时只想"这个值对不对"，
　　　　没想到"还有谁在用老坐标" → 另一任务位移从 700px 缩到 17px。

### 纪律 2 —— 宣布"统一/重构完成"前，必须贴出全量搜索结果

> **完成的定义 = 旧模式搜索为空。**

❌ 反例：建好统一动作、改了主流程就宣布完成 → 实际还剩 9 处手写坐标。

### 纪律 3 —— 一次只改一件事

> **多改叠加的直接后果：出问题时无法二分定位，只能全部回滚。**

用户原话（本项目）：
> 「你一个一个来啊，一次会话只执行 1 个方案，不然我没法及时反馈…
> 　最后也没搞清楚到底哪个在起作用」

## 5. 验收：分层 + 可判定

### 5.1 分层标准

| 层 | 内容 | 谁验 | 本项目 |
|---|---|---|---|
| **L1** | 语法通过、加载成功、版本号正确 | 我，**自动** | ✅ |
| **L2** | 探针喂正负样本 → 输出符合预期 | 我，**自动** | ❌ **完全缺失** |
| **L3** | 动作落点在安全区、日志无异常 | 我 + 用户看日志 | ⚠️ 部分 |
| **L4** | 单任务真机端到端跑通一次 | **用户** | ⚠️ |
| **L5** | 连续 N 轮稳定，无卡死/无残留 | **用户** | ❌ |
| **L6** | 异常恢复（中断无残留、卡住自动退） | **用户** | ❌ |

> **L1/L2 必须自动化** —— 这是唯一**不需要用户参与**、且能拦住大部分低级错误的两层。
> 本项目 L2 完全缺失 → **所有阈值问题都漏到了 L4**。

### 5.2 交付物模板（固定格式）

每次交付必须附：

```
① 语法检查结果
② 涉及改动的全量 grep（证明无残留）
③ 探针正负样本实测值（若改了判据）
④ 期望日志样例   ← 让用户"对照"，而不是"描述现象"
```

> **④ 最易被忽略，但价值最高**：
> 给用户一段「跑对了应该长什么样」的日志，用户看一眼就能判断，
> **不需要描述现象，我也不需要猜。**

## 6. 通用原则（可迁移到任何"视觉驱动自动化"任务）

1. **负样本比正样本重要**
   正样本告诉你"目标存在"，负样本才告诉你"边界在哪"。**没有负样本的阈值都是猜的。**

2. **有歧义的表述必须在开工时消灭**
   不能靠记忆和默契，要固化进 API 命名。

3. **只能从用户获取的信息，一次性问完**
   意图、方向、容忍度、正负样本 —— 用户花 5 分钟，我省 5 轮返工。

4. **先建验证工具，再动主脚本**
   主脚本反馈周期以"轮"计，工具以"秒"计。

5. **局部改完 ≠ 全局改完**
   改共享资源先清点影响面；宣布完成前贴全量搜索。

6. **一次只改一件事**
   保证可二分定位。

7. **验收要可判定**
   给出「期望日志」，让用户对照，而不是让用户复述现象。

---

## 7. 一句话总结

> **这类任务的所有弯路，都可以归成一句话：**
> **我拿着"只能从你那里得到的信息"去猜。**
>
> **方法论的核心：识别出哪些信息是"只能用户提供"的
> （意图、方向、容忍度、负样本），开工时一次性问完；
> 其余能自动化的（工具、验证），提前建好。**
>
> **猜的部分越少，弯路就越少。**
